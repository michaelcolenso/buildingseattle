# Repository Guidelines

## Project Structure & Module Organization

This repository is a Cloudflare Worker application (~10,500 lines in `worker.js`, with pure/shared logic split into sibling modules) with a Python ingestion pipeline. `worker.js` contains the edge backend, route handling, SQL calls, and inlined HTML responses. Sibling modules: `entity_graph.js` (entity derivation), `sdci_mappings.js` (status, neighborhood and type mappings shared with Python via `data/sdci_mappings.json`), `adu.js` (ADU/DADU classification), `entity_hubs.js` (hub-page SEO config), `value_counting.js` (how permit values are summed: a valuation SDCI repeats across a project's demolition permits counts once; use `countedValueSql()` in any `SUM` of value), `basis_reset.js` and `basis_reset_routes.js` (Basis Reset Radar), `mcp.js` (MCP server at `/mcp`), `security.js` (rate limits, Origin checks, Turnstile, API-key tiers, strict param parsing), `edge_cache.js` (HTML cache keys and TTLs) and `page_views.js` (sampled page-view logging and retention). **Never add non-function named exports to `worker.js`**: the Workers runtime rejects them and `wrangler dev` fails at startup; put shared constants in a sibling module. `schema.sql` is the complete current schema (no seed data). Schema changes are numbered `wrangler d1 migrations` files in `migrations/` (`0000_baseline.sql` is production as of 2026-11-27); every change needs a new `migrations/NNNN_*.sql` **and** the matching `schema.sql` edit, which `tests/schema_migrations.test.js` checks. The old hand-applied `migration_*.sql` files are history in `migrations/legacy/`. The one-time production bootstrap of the `d1_migrations` table is in `CLAUDE.md` ("Database migrations"). A daily cron (`0 13 * * *`) runs the incremental base-feed ingest plus a weekly full sweep (`sdci_feed.js`, `permit_upsert.js`; there is no wipe/replace-all path), entity-graph rebuild and alert sending (the rebuild is incremental and logs its own `run_type = 'entity_graph'` row in `ingest_logs`; see `CLAUDE.md`); `.github/workflows/enrich-daily.yml` enriches permits an hour later via `scripts/enrich_unenriched.py` (new permits plus a bounded rotation of stale ones; queue SQL in `scripts/enrichment_queue.py`; posts to the apex, `WORKER_URL` overrides). Python data collection and import scripts live at the repo root in `sdci_scraper.py` and `direct_import.py`. The Gumroad dataset product lives in `gumroad/` — rebuild it with `python3 gumroad/build_dataset.py` (paid files go to gitignored `gumroad/dist/`), never hand-edit the CSVs. Superseded one-off scripts (including the old `enrich_sdci.py`) live in `scripts/legacy/`; root `sdci_detail_probe.py` is a live dependency of the enrichment scripts, not a one-off. SEO monitoring lives in `scripts/check_seo_health.mjs` (daily via `.github/workflows/seo-health.yml`) and the manual `scripts/seo_investigation/` toolkit (own `requirements.txt`, gitignored `.seo_data/`). Design/brand direction for HTML pages is in `.impeccable.md`; investigation notes are in `docs/`. Runtime configuration is in `wrangler.toml`, and Python dependencies are declared in `pyproject.toml`.

**Generated-artifact policy:** never commit generated data (JSONL exports, `sql_*.sql` import chunks, `.b64` image blobs, `gumroad/dist/`) — these are gitignored. Regenerate them via the relevant script instead.

## Build, Test, and Development Commands

- `npx wrangler dev`: run the Worker locally on Cloudflare's dev server.
- `npx wrangler deploy`: deploy the Worker.
- `npx wrangler d1 execute buildingseattle --local --file schema.sql`: create a fresh local database.
- `npx wrangler d1 migrations apply buildingseattle --local` (then `--remote`): apply pending schema migrations.
- `npx wrangler d1 execute buildingseattle --remote --command "SELECT COUNT(*) FROM permits"`: inspect live data quickly (read-only queries only).
- `uv sync --extra dev`: install Python dependencies (including test tooling).
- `python sdci_scraper.py`: fetch permit data and write fresh JSONL files.
- `python direct_import.py`: send local JSONL records to the running Worker (requires `INGEST_API_TOKEN`).
- `uv run --extra dev pytest tests/`: run Python tests.
- `npm test` (or `node --test "tests/**/*.test.js"`): run Worker/JS tests. Single file: `node --test tests/entity_graph.test.js`; single test: add `--test-name-pattern="name"`.
- `uv run --extra dev pytest tests/test_direct_import.py -k name`: run one Python test.
- `node --check worker.js`: syntax check (CI runs it).
- `python3 gumroad/build_dataset.py`: rebuild the Gumroad dataset product end to end.

## Coding Style & Naming Conventions

Match the existing style instead of introducing new patterns. In `worker.js`, use 2-space indentation, semicolons, double quotes, and small route/helper functions where practical. In Python, use 4-space indentation, snake_case names, and short docstrings for non-obvious helpers. Keep SQL parameterized through D1 `prepare().bind()`. SDCI status and neighborhood mappings live only in `data/sdci_mappings.json` (read by `sdci_mappings.js` and `sdci_mappings.py`); permit-type classification is still duplicated in `sdci_scraper.py` and `worker.js`, so keep those two in sync.

## Testing Guidelines

Test files live under `tests/`. Node's built-in runner covers the Worker and its modules (`worker.test.js`, `edge_cache.test.js` (cache keys, admin no-store), `page_views.test.js` (bot skip, retention), `schema_migrations.test.js` (schema.sql equals migrations), `entity_graph.test.js`, `entity_rebuild.test.js` (incremental rebuild on SQLite), `empty_address.test.js` (410 vs 503), `mcp.test.js`, `basis_reset*.test.js`, `entity_hub_sql.test.js`, `project_dedupe.test.js`, `homepage.test.js`, `seo_health.test.js`, and others). Pytest (some `pytest-asyncio`) covers the Python side: `test_direct_import.py`, `test_sdci_enrich.py`, `test_build_dataset.py`, `test_basis_reset_candidates.py`, `test_url_inspection.py`, `test_enrichment_queue.py`, `test_workflows.py`. CI (`.github/workflows/test.yml`) runs both suites plus `node --check worker.js` on every push/PR. Scheduled workflows report failures through the reusable `notify-failure.yml` (one `[Workflow failure]` issue per workflow); `data-freshness.yml` runs `scripts/check_freshness.py` against `/api/stats` daily. Pin third-party actions to full commit SHAs and pass dispatch inputs through `env:`. For Worker changes, also verify locally with `npx wrangler dev` and exercise `/api/permits`, `/api/stats`, and any modified ingest route before opening a PR.

## Commit & Pull Request Guidelines

Follow the existing history: short, imperative subjects, optionally prefixed with the area (e.g. `url_inspection: validate --urls before signing in`). Keep commits focused by separating Worker, schema, and data-refresh changes where possible. PRs should include a concise summary, linked issue if applicable, schema or ingest notes, and screenshots for landing-page or HTML output changes.

## Security & Configuration Tips

Do not change the D1 binding or database ID in `wrangler.toml` without a migration plan. The ingest endpoints require the `X-Ingest-Token` header (checked against `env.INGEST_API_TOKEN`), and admin endpoints require `X-Admin-Token` (`env.ADMIN_API_TOKEN`); admin POSTs accept only that header and refuse cross-site Origins. Public forms (`/leads`, `/alerts/*`) are same-origin only and rate-limited; `/api/permits` and MCP serve anonymous callers a capped sample and full access with `X-API-Key` (`env.API_KEYS` or the `api_keys` table). The CSP forbids inline scripts (except the hashed theme boot script) and inline `on*` handlers: put page behaviour in static files under `public/brand/`. Set both via `.dev.vars` locally — never commit that file, it's gitignored. Treat large JSONL/SQL files as generated artifacts and never commit them. The repo is public: in `gumroad/` only the free sample CSV, the dictionary, `VERSION.txt` and `CHANGELOG.md` are tracked; the paid full CSV, contractor CSV and ZIPs are built into gitignored `gumroad/dist/` and uploaded to Gumroad only.
